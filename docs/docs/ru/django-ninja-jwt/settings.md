
Некоторые аспекты поведения Ninja JWT можно настроить с помощью переменных настроек в `settings.py`:

```python
# Django project settings.py

from datetime import timedelta
from django.conf import settings
...

NINJA_JWT = {
    'ACCESS_TOKEN_LIFETIME': timedelta(minutes=5),
    'REFRESH_TOKEN_LIFETIME': timedelta(days=1),
    'ROTATE_REFRESH_TOKENS': False,
    'BLACKLIST_AFTER_ROTATION': False,
    'UPDATE_LAST_LOGIN': False,

    'ALGORITHM': 'HS256',
    'SIGNING_KEY': settings.SECRET_KEY,
    'VERIFYING_KEY': None,
    'AUDIENCE': None,
    'ISSUER': None,
    'JWK_URL': None,
    'LEEWAY': 0,

    'USER_ID_FIELD': 'id',
    'USER_ID_CLAIM': 'user_id',
    'USER_AUTHENTICATION_RULE': 'ninja_jwt.authentication.default_user_authentication_rule',

    'AUTH_TOKEN_CLASSES': ('ninja_jwt.tokens.AccessToken',),
    'TOKEN_TYPE_CLAIM': 'token_type',
    'TOKEN_USER_CLASS': 'ninja_jwt.models.TokenUser',

    'JTI_CLAIM': 'jti',

    'SLIDING_TOKEN_REFRESH_EXP_CLAIM': 'refresh_exp',
    'SLIDING_TOKEN_LIFETIME': timedelta(minutes=5),
    'SLIDING_TOKEN_REFRESH_LIFETIME': timedelta(days=1),
    
    # For Controller Schemas
    # FOR OBTAIN PAIR
    'TOKEN_OBTAIN_PAIR_INPUT_SCHEMA': "ninja_jwt.schema.TokenObtainPairInputSchema",
    'TOKEN_OBTAIN_PAIR_REFRESH_INPUT_SCHEMA': "ninja_jwt.schema.TokenRefreshInputSchema",
    # FOR SLIDING TOKEN
    'TOKEN_OBTAIN_SLIDING_INPUT_SCHEMA': "ninja_jwt.schema.TokenObtainSlidingInputSchema",
    'TOKEN_OBTAIN_SLIDING_REFRESH_INPUT_SCHEMA':"ninja_jwt.schema.TokenRefreshSlidingInputSchema",
    
    'TOKEN_BLACKLIST_INPUT_SCHEMA': "ninja_jwt.schema.TokenBlacklistInputSchema",
    'TOKEN_VERIFY_INPUT_SCHEMA': "ninja_jwt.schema.TokenVerifyInputSchema",
}
```

Выше показаны значения по умолчанию для этих настроек.

## `ACCESS_TOKEN_LIFETIME`

Объект `datetime.timedelta`, определяющий время жизни access-токенов.
При генерации токена это значение `timedelta` добавляется к текущему времени UTC для получения значения claim `exp` токена по умолчанию.

## `REFRESH_TOKEN_LIFETIME`

Объект `datetime.timedelta`, определяющий время жизни refresh-токенов.
При генерации токена это значение `timedelta` добавляется к текущему времени UTC для получения значения claim `exp` токена по умолчанию.

### ``BLACKLIST_AFTER_ROTATION``
----------------------------
Если установлено значение ``True``, и используется приложение чёрного списка, и ``ROTATE_REFRESH_TOKENS`` установлен в ``True``,
refresh-токены, отправленные в ``TokenRefreshView``, будут добавлены в чёрный список.
Чтобы использовать эту настройку, вам нужно добавить ``'ninja_jwt.token_blacklist'`` в ``INSTALLED_APPS`` в вашем файле настроек.


Узнайте больше о `/blacklist_app`{.interpreted-text role="doc"}.

## `UPDATE_LAST_LOGIN`

Если установлено значение `True`, поле last_login в таблице auth_user обновляется при входе в систему (TokenObtainPairView).

    Предупреждение: обновление времени последнего входа значительно увеличит количество транзакций в базе данных.
    Злоупотребление этим представлением может замедлить работу сервера, что может стать уязвимостью в системе безопасности.
    Если вы действительно хотите это сделать, хотя бы ограничьте эндпоинт троттлингом.

## `ALGORITHM`

Алгоритм из библиотеки PyJWT, используемый для выполнения операций подписи/верификации токенов.
Для симметричной подписи и верификации HMAC вы можете использовать следующие алгоритмы: ``'HS256'``, ``'HS384'``,``'HS512'``.
При выборе алгоритма HMAC настройка ``SIGNING_KEY`` будет использоваться и как ключ подписи, и как ключ верификации.
В этом случае настройка ``VERIFYING_KEY`` игнорируется.
Для асимметричной подписи и верификации RSA вы можете использовать следующие алгоритмы: ``'RS256'``, ``'RS384'``, ``'RS512'``.
При выборе алгоритма RSA настройка ``SIGNING_KEY`` должна быть установлена в строку, содержащую приватный RSA-ключ.
Аналогично, настройка ``VERIFYING_KEY`` должна быть установлена в строку, содержащую публичный RSA-ключ.

## `SIGNING_KEY`

Ключ подписи, используемый для подписи содержимого генерируемых токенов.
Для подписи HMAC это должна быть случайная строка, содержащая не менее стольких бит данных, сколько требуется протоколом подписи.
Для подписи RSA это должна быть строка, содержащая приватный RSA-ключ длиной 2048 бит или более.
Поскольку Simple JWT по умолчанию использует подпись HMAC с 256-битным ключом, настройка `SIGNING_KEY` по умолчанию принимает значение настройки `SECRET_KEY` вашего Django-проекта.
Хотя это наиболее разумное значение по умолчанию, которое может предоставить Simple JWT, разработчикам рекомендуется изменить эту настройку на значение, независимое от секретного ключа Django-проекта.
Это упростит замену ключа подписи в случае компрометации ключа, используемого для подписи токенов.

## `VERIFYING_KEY`

Ключ верификации, используемый для проверки содержимого генерируемых токенов. Если настройка ``ALGORITHM`` указывает алгоритм HMAC,
настройка ``VERIFYING_KEY`` игнорируется, и вместо неё используется значение ``SIGNING_KEY``.
Если настройка ``ALGORITHM`` указывает алгоритм RSA, настройка ``VERIFYING_KEY`` должна быть установлена в строку, содержащую публичный RSA-ключ.

## `AUDIENCE`

Claim «аудитория», включаемый в генерируемые токены и/или проверяемый в декодированных токенах.
Если установлено значение ``None``, это поле исключается из токена и не проверяется.

## `ISSUER`

Claim «издатель», включаемый в генерируемые токены и/или проверяемый в декодированных токенах.
Если установлено значение ``None``, это поле исключается из токена и не проверяется.

### ``JWK_URL``
----------

JWK_URL используется для динамического разрешения публичного ключа, необходимого для проверки подписей токенов.
Например, при использовании Auth0 вы можете установить это значение в 'https://yourdomain.auth0.com/.well-known/jwks.json'.
Если установлено значение ``None``, это поле исключается из токен-бэкенда и не используется при верификации

### ``LEEWAY``
----------

Leeway (допуск) используется, чтобы дать некоторый запас для времени истечения срока действия. Это может быть целое число секунд или ``datetime.timedelta``.
Для получения дополнительной информации обратитесь к https://pyjwt.readthedocs.io/en/latest/usage.html#expiration-time-claim-exp.

###``AUTH_HEADER_TYPES``
---------------------

Тип(ы) заголовка авторизации, которые будут приниматься представлениями, требующими аутентификации. Например, значение ``'Bearer'`` означает, что представления, требующие аутентификации, будут искать заголовок следующего формата:
``Authorization: Bearer <token>``. Эта настройка также может содержать список или кортеж возможных типов заголовков (например, ``('Bearer', 'JWT')``).
Если используется список или кортеж, и аутентификация не удалась, первый элемент коллекции будет использован для формирования заголовка «WWW-Authenticate» в ответе.

###``AUTH_HEADER_NAME``
----------------------------

Имя заголовка авторизации, используемого для аутентификации. По умолчанию это `HTTP_AUTHORIZATION`, что означает приём заголовка `Authorization` из запросов.
Например, если вы хотите использовать `X_Access_Token` в заголовках запросов, укажите `AUTH_HEADER_NAME` как `HTTP_X_ACCESS_TOKEN` в своих настройках.


###``USER_ID_FIELD``
-----------------

Поле в модели пользователя базы данных, которое будет включаться в генерируемые токены для идентификации пользователя.
Рекомендуется, чтобы значение этой настройки указывало на поле, которое обычно не меняется после выбора своего начального значения.
Например, указание поля «username» или «email» было бы плохим выбором,
поскольку имя пользователя или email аккаунта могут измениться в зависимости от того, как устроено управление аккаунтами в конкретном сервисе.
Это может позволить создать новый аккаунт со старым именем пользователя, в то время как существующие токены, использующие это имя пользователя в качестве идентификатора пользователя, останутся валидными.

###``USER_ID_CLAIM``
-----------------

Claim, используемый для хранения идентификатора пользователя в генерируемых токенах. Например, установка значения ```"user_id"``` означает, что сгенерированный токен содержит claim «user_id»,
который содержит идентификатор пользователя.

###``USER_AUTHENTICATION_RULE``
----------------------------

Вызываемый объект, используемый для определения того, разрешено ли пользователю проходить аутентификацию. Это правило применяется после обработки валидного токена. Объект пользователя передаётся в качестве аргумента в вызываемый объект.
Правило по умолчанию проверяет, что флаг ``is_active`` по-прежнему равен ``True``.
Вызываемый объект должен возвращать логическое значение: ``True`` означает авторизован, ``False`` — в противном случае, что приводит к коду состояния 401.

###``AUTH_TOKEN_CLASSES``
----------------------

Список путей с точками, указывающих на классы, которые определяют допустимые типы токенов для подтверждения аутентификации. Подробнее в разделе «Типы токенов» ниже.

###``TOKEN_TYPE_CLAIM``
--------------------

Имя claim, используемого для хранения типа токена. Подробнее в разделе «Типы токенов» ниже.

###``JTI_CLAIM``
-------------

Имя claim, используемого для хранения уникального идентификатора токена. Этот идентификатор используется для отзыва токенов в приложении чёрного списка.
В некоторых случаях может потребоваться использовать claim, отличный от «jti» по умолчанию, для хранения такого значения.

###``TOKEN_USER_CLASS``
--------------------

Нестационарный (stateless) объект пользователя, основанный на проверенном токене. Используется только бэкендом аутентификации JWTStatelessUser.
Значение — это путь с точками, указывающий на ваш подкласс ``"rest_framework_simplejwt.models.TokenUser"``, который также является значением по умолчанию.

###``SLIDING_TOKEN_LIFETIME``
--------------------------

Объект ``datetime.timedelta``, определяющий, как долго sliding-токен валиден для подтверждения аутентификации.
При генерации токена это значение ``timedelta`` добавляется к текущему времени UTC для получения значения claim «exp» токена по умолчанию.
Подробнее в разделе «Sliding-токены» ниже.

###``SLIDING_TOKEN_REFRESH_LIFETIME``
----------------------------------

Объект ``datetime.timedelta``, определяющий, как долго sliding-токен валиден для обновления.
При генерации токена это значение `timedelta` добавляется к текущему времени UTC для получения значения claim «exp» токена по умолчанию.
Подробнее в разделе «Sliding-токены» ниже.

###``SLIDING_TOKEN_REFRESH_EXP_CLAIM``
-----------------------------------

Имя claim, используемого для хранения времени истечения срока действия периода обновления sliding-токена. Подробнее в разделе «Sliding-токены» ниже.
